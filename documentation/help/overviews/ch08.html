Chapter 8 — Main Dispatcher State Machine

The main dispatcher is the central message-routing engine for the OpenLCB protocol stack. It lives in openlcb_main_statemachine.c/.h and is driven by a single entry point called as fast as possible from the application main loop.

Source files: src/openlcb/openlcb_main_statemachine.c, src/openlcb/openlcb_main_statemachine.h

8.1 Entry Point

The entire dispatch loop is driven by OpenLcbMainStatemachine_run(). Each call performs exactly one atomic operation and returns immediately, maintaining a non-blocking cooperative design. The application calls this as fast as possible: 

while (1) {
    OpenLcbMainStatemachine_run();   // protocol dispatch
    OpenLcbLoginMainStatemachine_run();  // login sequencing
    CanMainStateMachine_run();       // CAN layer
}

8.2 Priority Dispatch Flowchart

Each call to _run() does one step of work and returns. While a message is being shown to the other nodes on this device (the dispatch stack is active, see §8.6), the step is always taken on the stack. Otherwise the priorities below are evaluated in order, and the first one that does work returns.

Priority Function / Step Purpose
Stack (while active) _sibling_run_top() One step on the top level of the dispatch stack (§8.6). Nothing else runs until the stack is empty.
1 handle_outgoing_openlcb_message() Send the pending main outgoing message to the wire. On success, with more than one node, push it as level 1 of the dispatch stack so the other local nodes are shown it; the slot stays valid until that level finishes.
2 handle_try_reenumerate() If a main handler set the enumerate flag (multi-message response), re-enter the same handler on the same node. Runs only after the previous message has been sent and shown to the local nodes.
3 _handle_application_send_queue() With no incoming message in progress, send the oldest queued application message (§8.6) and push it as level 1.
4 handle_try_pop_next_incoming_openlcb_message() Pop the next message from the incoming FIFO (thread-safe under lock). Discards messages marked invalid.
5 handle_try_enumerate_first_node() Get the first node from the node pool and dispatch the incoming message to it.
6 handle_try_enumerate_next_node() Advance to the next node and dispatch. Frees the incoming message when the last node is reached.

8.3 The State Machine Contexts

The dispatcher maintains a main context plus one context per dispatch stack level, all of type openlcb_statemachine_info_t. They share the same protocol handler callbacks. 

typedef struct {
    openlcb_msg_info_t   incoming_msg_info;   // current incoming message + enumerate flag
    openlcb_msg_info_t   outgoing_msg_info;   // worker buffer for reply + valid flag
    openlcb_node_t      *openlcb_node;        // node currently being enumerated
    uint8_t              current_tick;         // snapshot of 100ms timer
} openlcb_statemachine_info_t;
InstanceVariablePurpose
Main context _statemachine_info Processes messages from the incoming FIFO; builds outgoing replies during normal node enumeration.
Stack levels _sibling_levels[USER_DEFINED_SIBLING_DISPATCH_STACK_DEPTH] One context per level of the dispatch stack (§8.6). Its incoming pointer is the message being shown to the local nodes, owned by the level below (or the main outgoing slot, or the application send queue); its own worker outgoing buffer holds the answer of the node currently being shown it.
Worker buffer: Every context (main and each stack level) pre-allocates a STREAM-sized outgoing buffer at initialization (the largest available), so any protocol handler can build a response without worrying about buffer size limits.

8.4 Node Address Filtering

Before dispatching a message to a protocol handler, the function OpenLcbMainStatemachine_does_node_process_msg() determines whether the current node should process the message. The rules are:

  1. If the node is NULL or not initialized, reject.
  2. If the message is a loopback from this same node (self-skip), reject.
  3. If the message is global (no destination address bit set), accept.
  4. If the message is addressed, accept only if the destination alias or Node ID matches this node.
  5. Special case: MTI_VERIFY_NODE_ID_GLOBAL is always accepted (it carries an optional Node ID in the payload).

8.5 Fan-Out to All Nodes

Every incoming message is dispatched to every node in the system by the enumerate-first / enumerate-next loop. Global messages reach all nodes; addressed messages are filtered by does_node_process_msg() so only the target node processes them. This fan-out design supports multi-node configurations where a single microcontroller hosts several virtual nodes.

8.6 Delivery Between Local Nodes (Dispatch Stack)

When a node sends a message (e.g., Init Complete, a PCER), the other virtual nodes on the same device must also see it, because the CAN hardware does not loop transmitted frames back to the local receive path. Chapter 21 covers the design; this section covers how the run loop does it.

Mechanism

  1. A message a local node sends goes to the wire first.
  2. With more than one node, it is then pushed as a level of the dispatch stack (_sibling_push()): the level points at the message (no copy), marks it loopback = true so the sender skips its own copy in does_node_process_msg(), and starts at the first node.
  3. Each _run() call then does one step on the top level (_sibling_run_top()):
    • if the node just shown the message answered, the answer is sent to the wire (retried until the transport takes it) and pushed as the next level, so it is shown to the local nodes before this level continues;
    • if the node set the enumerate flag (several messages), it is called again, on the same node, once its previous message has finished;
    • otherwise the message is shown to the next node that has sent Initialization Complete (state.initialized);
    • when every node has been shown it, the level finishes and releases the message to its owner.

Depth

The stack grows with how far answers chain, not with the number of nodes: a node's answer is finished before the next node is shown the original message. Unaddressed answers stop at depth 2, a datagram exchange between two local nodes needs 3, and train listener forwarding between local trains needs the consist depth. USER_DEFINED_SIBLING_DISPATCH_STACK_DEPTH (default 4, at most OPENLCB_SIBLING_DISPATCH_STACK_DEPTH_MAX = 8) sets the size. A message that would go deeper is still sent to the wire but is not shown to the local nodes; it is counted.

Order: the wire sees messages in the order they are sent. Other local nodes can see an answer before the request it answers: if Node A's global Verify Node ID is shown to Node B first, B's Verified Node ID is shown to Node C before A's Verify is.

Application Send Queue

Messages from application code, the login state machine, the train, Broadcast Time and DCC CV helpers and the config-memory stream pump go through OpenLcbMainStatemachine_send_with_sibling_dispatch(). With one node it sends straight to the transport. With several, it copies the message into the application send queue (USER_DEFINED_APPLICATION_SEND_QUEUE_DEPTH, default 4) and returns true (accepted, not yet on the wire), or false when the queue is full (retry later). The queue is drained oldest first when the stack is empty and no incoming message is being processed, so everything a message caused goes out before the next incoming message is handled.

Callbacks: a send from inside a callback goes into the queue like any other application send. Never loop waiting for a send to succeed inside a callback: the queue only drains after the callback returns. A false there means the queue is full; keep the message and send it from the main loop.
Buffer pressure: No dynamic allocation is used. Each level and each queue entry is a statically allocated worker buffer. Each node is shown a message in one _run() call; the CAN RX ISR continues filling its software FIFO independently, so no frames are lost.

8.7 The Enumerate Flag

Some protocol handlers need to send multiple messages in response to a single incoming message. For example, Identify Events must report every producer and consumer event the node knows about. The mechanism:

  1. The handler builds the first response, sets outgoing_msg_info.valid = true, and sets incoming_msg_info.enumerate = true.
  2. Priority 1 sends the outgoing message and, with several nodes, it is shown to the other local nodes on the dispatch stack.
  3. Priority 2 sees the enumerate flag and re-enters the handler on the same node. On a stack level the same rule applies: the node is called again only after its previous message has finished.
  4. The handler builds the next response. When the last message is sent, it clears the enumerate flag.
  5. The dispatcher advances to the next node (or the next incoming message).

8.9 Special MTI Intercepts

Several MTIs have special routing before falling through to the normal event transport handlers:

  • MTI_PRODUCER_IDENTIFY (0x0914): If the event ID is a train search event, it is dispatched to train_search_event_handler for train nodes only. If no train matches across all nodes, train_search_no_match_handler fires on the last node.
  • MTI_PRODUCER_IDENTIFIED_SET (0x0544): If the event ID is a broadcast time event, it is dispatched to broadcast_time_event_handler (node index 0 only).
  • MTI_PC_EVENT_REPORT (0x05B4): Checked first for broadcast time events (node 0 only), then for emergency events (dispatched to all train nodes), before falling through to the regular event handler.

8.10 Interaction Rejected

OpenLcbMainStatemachine_load_interaction_rejected() builds an OIR response with error code ERROR_PERMANENT_NOT_IMPLEMENTED_UNKNOWN_MTI_OR_TRANSPORT_PROTOCOL and includes the triggering MTI in the payload (bytes 2-3). This is called:

  • When a request-type MTI has a NULL handler callback.
  • For any unknown addressed MTI in the default case.
  • Unknown global MTIs are silently ignored (no OIR).
