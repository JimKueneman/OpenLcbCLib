Chapter 21 — Multi-Node Message Routing

A single physical device can host multiple virtual OpenLCB nodes — for example, a command station might host one configuration node plus several train nodes. Each virtual node has its own unique 48-bit Node ID and its own 12-bit CAN alias. From the perspective of other devices on the CAN bus, each virtual node is an independent node.

Implementation: local delivery is done by the dispatch stack and the application send queue in openlcb_main_statemachine.c. The login state machine, the application helpers and the config-memory stream pump all send through OpenLcbMainStatemachine_send_with_sibling_dispatch(). See also Ch 8 §8.6 for how the run loop does it.

21.2 The Loopback Problem

When virtual Node A transmits a message, the CAN hardware does not deliver that frame back to the local receive path. Remote nodes on the bus see it, but co-hosted sibling nodes do not.

Without a fix, this affects every protocol:

ProtocolImpact without sibling dispatch
Event TransportNode A produces an event; co-hosted Node B that consumes it never sees the PCER.
DatagramsNode A sends a datagram addressed to Node B; Node B never receives it.
Train ControlA local throttle node sends speed commands to a co-hosted train node; the train never responds.
Verify Node IDGlobal Verify from Node A should elicit a response from Node B; without loopback it does not.
Init CompleteNode A's Init Complete must be seen by Node B to update its listener alias table; without loopback it is missed.

21.3 The Rule: Finish Each Message Before Moving On

Every message a local node sends goes to the wire first and is then shown to every other local node, one node per _run() call, before the loop moves on. If a node answers while it is being shown the message, its answer is finished the same way (wire, then every other local node) before the original message is shown to the next node. The loop keeps track of this on a small stack: one level per message in progress.

Only one answer is in progress at any moment, so a request answered by every node on a 50-node device needs no more storage than one answered by a single node.

Order: the wire sees messages in the order they are sent. Another local node can see an answer before the request it answers (Node C above sees B's Verified before A's Verify). Wire order is unchanged.

21.4 Answers of Several Messages

A handler that answers with several messages (Identify Events, a train forwarding a command to its listeners, Datagram Received OK followed by the reply datagram) sets the enumerate flag. The node is called again for its next message only after the previous one has gone to the wire and been shown to every other local node, and always on the same node. Two hundred Identified messages use one level, one after another.

21.5 Stack Depth

The stack grows with how far answers chain, not with how many nodes answer:

Traffic between local nodesLevels
Global request answered by every node (Verify, Identify Events)2
Datagram exchange (request, Datagram OK and reply, acknowledgement)3
Star consist: throttle to lead train, lead forwards to each member2
Daisy-chained consist of local trains (A lists B, B lists C, ...)1 per train, plus 1

A chain cannot pass through more local nodes than the device has, so the stack is sized USER_DEFINED_NODE_BUFFER_DEPTH + 2 and needs no setting. A level holds only pointers and a node position; nodes are walked with OpenLcbNode_get_by_index().

21.6 Where the Messages Live

  • A message from the wire stays in its buffer-store buffer; the dispatcher points at it.
  • A node's answer is written into one shared worker buffer and copied into the smallest buffer-store buffer that holds it (BASIC, DATAGRAM, SNIP or STREAM) as soon as the handler returns. If none is free, the copy is retried on the next pass before anything else runs.
  • An application send on a device with more than one node is copied into a buffer-store buffer and queued (see 21.7).

Answers and queued sends share the buffer store with received messages, so a busy multi-node device may need larger pools (USER_DEFINED_BASIC_BUFFER_DEPTH and friends). No dynamic allocation is used.

21.7 Application Sends

The application helpers, the train and Broadcast Time helpers, DCC CV deferred replies, the login state machine and the config-memory stream pump all send through OpenLcbMainStatemachine_send_with_sibling_dispatch():

  • One node: the message goes straight to the transport and the result is the transport's.
  • Several nodes: the message is copied into a buffer-store buffer and queued. The call returns true when accepted (not yet on the wire) or false when the buffer store is empty; retry later. The queue has one slot per buffer-store buffer, so size the buffer pools for the largest burst the application sends (including from callbacks) plus the incoming messages waiting to be processed. Queued messages are sent oldest first when the stack is empty and no incoming message is being processed, so everything a message caused goes out before the next incoming message is handled.
Callbacks: a send from inside a callback is queued like any other. Never loop waiting for a send to succeed inside a callback; the queue only drains after the callback returns. Keep the message and send it again from the main loop.

Messages addressed to another local node still go out on the wire as well, so bus monitors such as JMRI see all traffic.

21.8 Which Nodes Are Shown a Message

A node is shown messages once it has sent Initialization Complete (state.initialized), including while it is still announcing its events. An Identify Events that arrives in that window restarts the node's announcements instead of being answered directly (see Ch 9). The sender never sees its own message (state.loopback). Addressed messages are handled only by their destination.

21.9 Per-Node Alias Allocation

Each virtual node goes through the full CAN login sequence independently via round-robin processing in the CAN main state machine. The login state machine iterates through all nodes not yet in RUNSTATE_RUN, running one state transition per node per main loop iteration. All nodes log in concurrently, each generating its own alias from its own Node ID seed.

21.10 Single-Node Devices

With one node there is nobody to show messages to: nothing is pushed on the stack and application sends go straight to the transport. The only cost is the stack's few bytes of bookkeeping.
